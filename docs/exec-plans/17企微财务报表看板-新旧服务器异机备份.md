# 项目 17 新旧服务器异机备份实施计划

## 目标

将新生产服务器 `8.163.36.95` 上项目 17 的一致性数据库快照、上传原件及必要恢复配置，经 SSH/rsync 增量推送到旧服务器 `8.163.95.203`，每天北京时间 `00:15、08:15、16:15` 执行一次，使异机备份 RPO 不超过 8 小时。旧服务器只作为备份节点，不重新部署或运行项目 17。

## 安全与数据边界

- 新服务器先调用应用自带的 `deploy/backup-database.mjs` 生成 SQLite 一致性快照，不直接复制运行中的主库、WAL 或 SHM。
- rsync 复用 SSH 22 端口，不启用 rsync daemon，不开放额外公网端口。
- 旧服务器使用独立 `wecom-finance-backup` 账号和专用目录，密钥只接受新服务器公网 IP，禁用端口转发、代理转发和 PTY。
- 不使用 `--delete`；新服务器上的误删不得传播到旧服务器。
- 上传原件长期保留；数据库与配置快照默认保留 90 天，由旧服务器本地 root 定时清理，推送端无删除权限。
- 生产环境配置只进入权限为 `0700/0600` 的备份目录，不输出内容到日志或对话。
- 旧服务器已有的 `wecom-finance-backup.timer` 先审计用途，不覆盖、不停止；本方案使用独立的 `wecom-finance-offsite-backup` 命名。

## 实施步骤

1. 只读核对两台服务器磁盘、系统、SSH 连通性、现有定时任务及备份目录。
2. 在旧服务器安装 rsync，创建专用用户、受限 SSH 公钥、备份根目录及 90 天保留清理任务。
3. 在新服务器生成专用 Ed25519 密钥，安装备份脚本和 systemd service/timer。
4. 脚本每次先创建一致性数据库快照，再分别同步数据库备份、上传资料和带时间戳的恢复配置；并生成 SHA256 清单和 journal 日志。
5. 首次手动运行 service，验证旧服务器文件数量、体积、权限和哈希。
6. 从旧服务器复制一份数据库快照及配置到隔离临时目录，执行 SQLite 完整性检查；不得覆盖生产文件。
7. 核验 timer 下一次执行时间、失败状态、SSH 限制、无删除传播和回滚方式，并更新生产运维文档。

## 验收标准

- 新服务器 timer 为 enabled/active，下一次执行时间符合北京时间三次固定时点。
- 手工首备成功，旧服务器拥有数据库一致性快照、完整上传镜像、恢复配置和 SHA256 清单。
- 隔离恢复数据库 `integrity_check` 返回 `ok`，核心表行数与新服务器一致。
- 专用密钥不能获得交互式 shell，不能写出指定备份根目录，备份目录不允许其他普通用户读取。
- 两台服务器原有容器、Nginx 和既有定时任务保持正常，项目 17 生产健康接口继续返回当前版本。

## 回滚

- 新服务器停止并禁用 `wecom-finance-offsite-backup.timer`，移除对应 service、脚本和专用私钥。
- 旧服务器移除专用公钥和备份用户；备份数据默认保留，除非用户另行明确要求删除。
- 不触碰生产数据库、上传目录、项目容器或旧服务器已有 `wecom-finance-backup.timer`。

## 实施结果

- `2026-09-01` 已完成 rsync 官方签名包安装、专用账号、`rrsync -wo` 限制、独立密钥、首次全量备份、隔离恢复和 systemd 定时任务启用。
- 新服务器 `wecom-finance-offsite-backup.timer` 固定在北京时间 `00:15、08:15、16:15` 执行，首次手工运行和 systemd 沙箱内运行均成功。
- 旧服务器保存 55 个上传文件；首次数据库快照两端 SHA256 一致，隔离恢复 `integrity_check=ok`，核心表行数与生产一致。
- 专用密钥的交互式 shell 和 `..` 越界路径均被拒绝；旧服务器原有 `wecom-finance-backup.timer` 继续 active。
- 旧服务器 `wecom-finance-offsite-retention.timer` 已启用，数据库、配置和清单保留 90 天，上传原件不自动删除。
